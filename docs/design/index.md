# Дизайн‑система Agency OS

Цей розділ описує, як ми мислимо дизайн у проєкті, і служить «контрактом» між UI/UX‑дизайном та реалізацією у коді (Nuxt UI, Tailwind CSS, власні компоненти).

## 1. Принципи дизайну

- **Фокус на даних та робочих процесах**  
  Інтерфейс мінімалістичний, без зайвих візуальних ефектів. Пріоритет — швидке сприйняття даних, а не декоративність.

- **OS‑подібний інтерфейс**  
  Портал працює як «агентський OS»: панелі, таблиці, форми, бічні сайдбари. Користувач проводить у системі багато часу, тому дизайн має бути «спокійним» і передбачуваним.

- **Консистентність через токени та компоненти**  
  Усі візуальні рішення повинні спиратися на спільні токени (`theme.ts`, `tailwind.config.ts`) та повторно використовувані компоненти (`components/base`, `components/navigation`, `components/blocks`).

- **Доступність та читабельність**  
  Контраст, розмір шрифтів, відступи й стани елементів мають підтримувати зручність читання та взаємодії.

## 2. Дизайн‑токени

Дизайн‑токени реалізовані у файлах:

- `theme.ts` — основні дизайн‑токени (кольори, шрифти, радіуси).
- `tailwind.config.ts` — прив’язка токенів до Tailwind (fontFamily, borderRadius тощо).

### 2.1. Кольори

Ключові кольорові токени:

- **`primary`** — головний акцентний колір інтерфейсу.  
  Визначається в `theme.ts`:

  ```ts
  export const theme = {
    primary: 'violet',
    gray: 'slate',
    // ...
  }
  ```

  **Використання:**

  - основні CTA‑кнопки та дії;
  - активні елементи навігації;
  - ключові індикатори статусу (де це доречно).

- **`gray`** — базова нейтральна шкала.  
  Використовується для бекграундів, бордерів, вторинного тексту, елементів навігації.

- **Semantic‑кольори (success / warning / error)**  
  Використовуються у компонентах нотифікацій, алертів, статус‑тегів. Для нових макетів: semantic‑кольори повинні або базуватися на існуючих Tailwind‑кольорах, або бути попередньо узгоджені й додані як токени.

**Правило для дизайнерів:**  
Не вводити довільні нові кольори в макетах без домовленості про їх додавання в `theme.ts`/Tailwind. Нові акценти = нові токени.

### 2.2. Типографіка

Шрифти визначені в `theme.ts`:

```ts
fonts: {
  display: 'Poppins',
  sans: 'Inter',
  code: 'Fira Code',
  signature: 'Nothing You Could Do',
}
```

- **Display (`Poppins`)** — заголовки сторінок, великі маркетингові секції.
- **Sans (`Inter`)** — основний текст інтерфейсу, тіла статей, лейбли.
- **Code (`Fira Code`)** — фрагменти коду, технічні приклади.
- **Signature** — використовується лише в окремих декоративних елементах (наприклад, підпис у блоках‑тестимоніалах).

В `tailwind.config.ts` шрифти прив’язані до Tailwind:

```ts
fontFamily: {
  sans: ['var(--font-sans)', ...defaultTheme.fontFamily.sans],
  display: ['var(--font-display)', ...defaultTheme.fontFamily.serif],
  mono: ['var(--font-mono)', ...defaultTheme.fontFamily.mono],
  signature: ['var(--font-signature)', 'cursive', 'sans-serif'],
}
```

**Ієрархія тексту (рекомендація для Figma):**

- **H1** — основні заголовки сторінок / розділів порталу.
- **H2** — заголовки секцій усередині сторінок.
- **H3/H4** — заголовки блоків, карток, панелей.
- **Body** — стандартний текст, описи, лейбли.
- **Caption / Meta** — допоміжний текст, підписи, системні позначки (дата, статус, ID).

Не перевантажуйте один екран більше ніж 2–3 різними розмірами шрифтів.

### 2.3. Відступи (spacing) та layout

Ми спираємося на Tailwind‑шкалу відступів (4/8 px крок).  
Рекомендовані значення:

- **Між секціями сторінки**: `py-12`–`py-16` у маркетинговій частині, `py-6`–`py-8` у порталі.
- **Всередині картки/панелі**: `p-4`–`p-6` залежно від щільності інформації.
- **Між елементами форми**: `space-y-3`–`space-y-4`.

У макетах Figma бажано використовувати кратні 4 px відступи, щоб вони добре мапились на Tailwind‑класи.

### 2.4. Border radius

Глобальний радіус задається в `theme.ts`:

```ts
borderRadius: 'lg',
```

А у `borderRadiusMap` описані призначення для різних типів елементів:

```ts
export const borderRadiusMap = {
  lg: {
    card: '0.5rem',
    button: '0.5rem',
    input: '0.5rem',
    panel: '0.5rem',
  },
  full: {
    card: '0.75rem',
    button: '9999px',
    input: '9999px',
    panel: '0.75rem',
  },
  // ...
}
```

**Домовленості для дизайну:**

- **Картки, панелі** — за замовчуванням використовуємо `card`‑радіус поточного пресету (наприклад, ~8 px).  
- **Кнопки, інпути** — `button` та `input` відповідно (однаковий радіус у межах теми).
- **Чіпи / теги / pills** — округлий (`full`), якщо це логічно.

Не створюйте в макетах проміжних радіусів (наприклад, 6 px, 10 px), яких немає в токенах.

## 3. Теми та керування токенами через Directus

У майбутньому (або у кастомних проєктах на базі AgencyOS) можемо мати **декілька тем**: наприклад, `agency_light`, `agency_dark`, `minimal` тощо.  
Теми зберігаються як дані в Directus і керують значеннями токенів (кольори, шрифти, радіуси).

### 3.1. Колекція `themes` у Directus

Рекомендована структура колекції:

- **`key`** (`string`, унікальний) — системний ключ теми (`agency_light`, `agency_dark`).
- **`label`** (`string`) — дружня назва теми («Agency Light»).
- **`tokens`** (`json`) — обʼєкт з токенами:
  - `primary`, `gray`, додаткові кольори;
  - `borderRadius` (`none | sm | base | md | lg | xl | full`);
  - `fonts` (`display`, `sans`, `mono`, `signature`);
  - опційно: `surface`, `accent`, `danger` тощо.
- **`is_default`** (`boolean`) — чи є тема дефолтною.

Альтернатива: замість окремої колекції `themes` зберігати вибір теми/токени у сінглтоні `globals` (поле `current_theme` + `theme_tokens`).

### 3.2. Як Nuxt застосовує тему

На рівні Nuxt тема застосовується через **CSS‑змінні**, які вже використовуються в `tailwind.config.ts`:

- Nuxt отримує вибрані токени з Directus (`useDirectus` + `readSingleton('globals')` або `readItems('themes', ...)`).
- У плагіні/композаблі ці токени перетворюються на CSS‑змінні:
  - `--font-sans`, `--font-display`, `--font-mono`, `--font-signature`;
  - `--border-radius-card`, `--border-radius-button`, `--border-radius-input`, `--border-radius-panel`;
  - за потреби — додаткові змінні для кольорів.
- Tailwind читає ці змінні (через `fontFamily`/`borderRadius` в `tailwind.config.ts`) і застосовує тему без перекомпіляції CSS.

**Для дизайнера це означає:**  
усі кольори/шрифти/радіуси в макетах мають відповідати можливим значенням токенів; при зміні теми в Directus змінюється візуальне оформлення, але не змінюється структура компонентів.

### 3.3. Перемикач тем

Архітектурно можливі варіанти:

- **Глобальна тема** — обирається в `globals` (адмін Directus задає дефолтну тему для всього сайту/порталу).
- **Тема per‑tenant / per‑site** — окрема колекція `sites` або `organizations` з полем `theme` (rel до `themes`), тема вибирається за доменом/організацією.
- **Користувацький перемикач** — зберігає обрану тему в cookie/localStorage, при SSR тема зчитується й застосовується через CSS‑змінні.

## 4. Компоненти

У коді компоненти структуровані в основному в:

- `components/base` — базові елементи (текст, інпути, алерти, аватари, галереї, завантаження тощо).
- `components/navigation` — хедер, футер, навігація.
- `components/blocks` — маркетингові/контентні блоки (Hero, LogoCloud, Steps, Testimonials тощо).

### 4.1. Базові компоненти (`components/base`)

**Приклади атомів/молекул:**

- `VText`, `VLabel` — текстові елементи та лейбли.
- `VAlert` — нотифікації/алерти з semantic‑станами.
- `VAvatar`, `UserBadge` — відображення користувача.
- `VUpload`, `VSignature`, `VGallery`, `VVideo` — спеціалізовані елементи вводу/медіа.
- `VLoading`, `RadialProgress` — стани завантаження та прогресу.

**Очікування до макетів:**

- Для кнопок/інтерактивних елементів завжди показувати стани: default, hover, disabled (за потреби — loading, focus).
- Для алертів/нотифікацій чітко зазначати тип: success / info / warning / error.
- Для форм — витримувати однакові відступи між полями та групами полів.

### 4.2. Навігація (`components/navigation`)

- `TheHeader`, `TheFooter`, `VHorizontalNavigation`, `MenuItem`, `MobileMenu`, `MobileMenuItem`.

**Рекомендації для дизайну:**

- Основні навігаційні елементи (primary routes) мають стабільні позиції у хедері/сайдбарі.
- Активний пункт навігації підсвічується через `primary`‑колір + зміну бекграунду/іконки.
- Для мобільної навігації враховуйте обмеження по висоті екрану: не перевантажувати меню другорядними опціями.

### 4.3. Контентні блоки (`components/blocks`)

Блоки використовуються переважно в маркетинговій/публічній частині (див. `docs/components/blocks.md`, `docs/architecture/marketing-site.md`).

Приклади:

- `Hero`, `Cta` — основні вступні секції.
- `LogoCloud` — логотипи партнерів / клієнтів.
- `Steps` — покрокові інструкції/процеси.
- `Team`, `Testimonials`, `Quote` — соціальний доказ.
- `Gallery`, `Video`, `RawHtml`, `RichText` — контентні секції.

**Вимоги до макетів:**

- Кожен блок має чітку внутрішню структуру (заголовок, підзаголовок, опис, ілюстрація, CTA).
- Не змішуйте надто багато різних типів блоків в одному екрані — краще 2–3 великих секції, ніж 6–7 дрібних.
- Зберігайте одноманітні відступи між блоками на сторінці.

## 5. Як працювати дизайнеру з системою

1. **Починати з токенів**  
   Перед створенням нового макету — звіритись із поточними токенами (`theme.ts`, Tailwind‑класи). Усі кольори, шрифти, радіуси мають походити звідти.

2. **Збирати з існуючих компонентів**  
   Спершу намагатись скласти екран з наявних компонентів (`components/base`, `components/blocks`, `components/navigation`). Якщо чогось бракує — описати новий компонент як варіацію вже існуючого.

3. **Пропонувати нові компоненти через опис**  
   Для нового компонента в Figma:
   - коротко описати use case;
   - показати стани (default/hover/disabled/loading, пустий стан, error);
   - вказати, які токени використовуються (primary/gray, radius preset, spacing).

4. **Не створювати локальні «унікальні» стилі без токенів**  
   Усі нові візуальні патерни мають бути узгоджені й, за потреби, винесені в токени/компоненти в коді.

Додаткові UX‑патерни та шаблони сторінок дивіться у `docs/design/patterns.md`.

## 6. Майбутній розвиток дизайн‑системи

Нижче — ідеї для еволюції дизайн‑системи AgencyOS з урахуванням можливих змін у коді.

### 6.1. Багатотемність та токени «по ролях»

- **Multi-theme support**  
  - Розширити `theme.ts`/`themes` у Directus, щоб підтримувати кілька повноцінних тем (наприклад, `agency_light`, `agency_dark`, `minimal`, `high_contrast`);  
  - У Nuxt додати зручний API (композабль/плагін) для перемикання тем (`useTheme()`), що оновлює CSS‑змінні та, за потреби, додає клас теми на `<html>/<body>`.

- **Ролеві токени (semantic tokens)**  
  - Замість привʼязки чисто до Tailwind‑кольорів (`violet`, `slate`) ввести semantic‑рівень: `color.surface`, `color.onSurface`, `color.primary`, `color.onPrimary`, `color.danger`, тощо;  
  - У коді компоненти посилаються на semantic‑токени, а мапа semantic → конкретний колір визначається темою;  
  - Це полегшує зміну тем (включно з high‑contrast) без зміни компонентів.

**Можливі зміни в коді:**  
- введення обʼєкта semantic‑tokens у `theme.ts`;  
- невеликі рефакторинги компонентів для використання semantic‑класів/var’ів замість прямого Tailwind‑кольору.

### 6.2. Варіанти блоків як реєстр (registry)

Зараз варіанти блоків описуються умовно в коді (`props.data.variant`).  
Можна винести їх у **централізований реєстр**:

- окремий TypeScript‑обʼєкт (наприклад, `blockVariantsRegistry`) з описом:
  - ключа варіанту (`hero.image_left`);
  - доступних полів/обмежень;
  - технічних нотаток (чи потрібен зображенні, які breakpoints важливі тощо).

- відображення цього реєстру в Directus:
  - для полів `variant` у block‑колекціях використовувати fixed‑options, що збігаються з ключами реєстру;
  - документацією в Directus (опис варіанту) керувати з того ж джерела (можливе напівавтоматичне оновлення або ручна синхронізація).

**Можливі зміни в коді:**  
- створення єдиного `componentMap` + `variantMap` для Page Builderʼа;  
- спрощення блок‑компонентів за рахунок винесення логіки вибору layoutʼів у допоміжний хелпер/реєстр.

### 6.3. Більш глибока інтеграція з Directus (multi‑tenant / per‑site)

Якщо AgencyOS використовується як платформа для кількох агентств/порталів:

- **Per‑tenant теми:**
  - колекція `organizations` або `sites` зі зв’язком `theme` (до `themes`);  
  - SSR/route middleware обирає тему на основі домену/organization‑id і застосовує відповідні токени.

- **Per‑site компонування:**
  - у Directus для кожного `site` зберігати набір дозволених блоків / варіантів (білий список);  
  - Page Builder на фронтенді фільтрує/валідує блоки за цим списком (для запобігання «ломаних» сторінок).

**Можливі зміни в коді:**  
- додатковий контекст `site/tenant` у Nuxt (наприклад, через middleware або `useRuntimeConfig`);  
- розширення `useDirectus`/`useAppConfig` для роботи з multi‑tenant налаштуваннями.

### 6.4. Перевірка макетів/схеми на відповідність дизайн‑системі

На рівні процесу можна додати «soft‑validation»:

- **Lint дизайну (Figma → код):**
  - чек‑лист для дизайнерів (чи використовуються лише дозволені токени, варіанти блоків, стани);
  - автоматичні плагіни в Figma (опційно) для підсвічування невідомих токенів.

- **Lint схеми (Directus):**
  - міграції/скрипти, що перевіряють, чи всі значення `variant` відповідають відомим у коді;
  - CI‑перевірка, що теми в Directus мають повний набір обовʼязкових токенів (щоб не було «неповних» тем).

Ці кроки не обовʼязкові для старту, але допоможуть з часом підтримувати дизайн‑систему в чистому стані.
