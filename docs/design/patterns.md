# UX‑патерни та шаблони сторінок

Цей документ описує типові шаблони сторінок і UX‑патерни, які ми використовуємо в Agency OS, а також очікування до макетів для UI/UX‑дизайнера.

## 1. Типи сторінок

У системі є два основних типи інтерфейсів:

- **Маркетинговий сайт / контентні сторінки**  
  Публічні сторінки, що використовують блоки з `components/blocks` (Hero, Testimonials, LogoCloud, Steps тощо). Докладніше — `docs/architecture/marketing-site.md`, `docs/components/blocks.md`.

- **Портал / OS‑інтерфейс**  
  Робочі інтерфейси (CRM, OS‑панелі, списки, деталі, форми), переважно в шарі `layers/portal`. Докладніше — `docs/layers/portal.md`, `docs/architecture/portal.md`.

Маркетинговий сайт може бути більш виразним візуально, портал — більш утилітарним і щільним.

## 2. Варіанти блоків (variants) та шаблони сторінок

Більшість блоків Page Builderʼа (Hero, CTA, RichText, Steps тощо) можуть мати **різні варіанти відображення** — наприклад:

- Hero: зображення ліворуч/праворуч, full‑bleed, мінімалістичний;
- CTA: один/два CTA, вирівнювання по центру або ліворуч;
- Testimonials: сітка, карусель (якщо буде реалізовано).

У Directus для цього використовується поле `variant` у колекціях блоків (`block_hero`, `block_cta`, ...).  
У макетах важливо:

- чітко показати, який **variant** має бути використаний;
- дотримуватись обмеженого набору варіантів, які реально підтримуються в коді.

**Приклад (BlockHero):**

- `variant`: `default | image_left | image_right | full_bleed | minimal`
- `image_position`: `left | right` (додатковий параметр для layoutʼу).

У Vue‑компонентах (`components/blocks/*.vue`) варіант відображення обирається за `props.data.variant`:

- один компонент з умовними гілками (`v-if`/`v-else-if` для різних layoutʼів); або
- окремі субкомпоненти для кожного варіанту (`BlocksHeroImageLeft`, `BlocksHeroImageRight` тощо).

Для дизайнера: **варіанти — це фіксований набір layoutʼів, узгоджений з розробкою**, а не вільна творчість на кожен блок.

### 2.1. Як саме Directus керує варіантами блоків

На рівні Directus і коду є кілька шарів керованості:

- **1) Контент + прості параметри (що вже є)**  
  - поля на кшталт `image_position` (`left/right`), `alignment` (`left/center`), `hide_block` вже керують базовим виглядом;  
  - ці поля сприймаються як «налаштування» усередині одного варіанту компонента.

- **2) Варіанти (`variant`) як контрольований набір стилів (рекомендовано)**  
  - у кожній block‑колекції (`block_hero`, `block_cta`, ...) додається поле `variant` (типу `string` або `enum` з фіксованим списком);  
  - значення `variant` відповідають реалізованим у коді layoutʼам (наприклад, `hero.default`, `hero.image_left`, `hero.full_bleed`);  
  - Page Builder просто передає ці дані, а блок‑компонент на Nuxt‑боці вирішує, як саме рендерити кожен варіант.

- **3) Повністю вільні стилі з Directus (не рекомендується)**  
  - технічно можна зберігати, наприклад, Tailwind‑класи (`className`) в Directus і застосовувати їх напряму;  
  - але це руйнує дизайн‑систему, ускладнює підтримку та типізацію, і майже завжди призводить до «зоопарку» стилів;  
  - тому ми обмежуємося контрольованими `variant` + токенами теми (див. `docs/design/index.md`).

**Що потрібно змінити в коді, щоб Directus більше контролював стилі:**

1. Додати поля `variant` у відповідні block‑колекції в Directus (через темплейт).  
2. Розширити типи `Block*` у `types/blocks/*.ts`, додавши туди поле `variant`.  
3. Оновити `components/blocks/*.vue`, щоб вони:
   - читали `props.data.variant`;  
   - мали реалізовані layoutʼи для всіх значень `variant`;  
   - використовували дизайн‑токени/класи, узгоджені з темою.

Після цього редактори в Directus зможуть керувати **варіантом відображення** кожного блоку без змін коду, але в межах наперед визначених та протестованих варіантів.

## 3. Шаблони сторінок порталу

### 3.1. Dashboard / список

Типовий шаблон списку (проекти, ліди, задачі тощо):

- **Структура:**
  - Заголовок сторінки (H1) + короткий опис (опціонально).
  - Панель дій: primary‑кнопка (створити / додати), фільтри, пошук.
  - Основний контент: таблиця або список карток.
  - Пагінація / індикатор кількості елементів.

- **UX‑правила:**
  - Primary‑дія завжди чітко виділена (`primary`‑кнопка справа вгорі).
  - Вторинні дії (експорт, масові операції) можна ховати в overflow‑меню.
  - Фільтри повинні бути візуально відокремлені від таблиці (панель або sticky‑рядок).

- **Для макетів Figma:**
  - Показати приклад заповненого стану (кілька рядків у таблиці) та порожнього стану (див. розділ 3.3).
  - Не перевантажувати верхню панель більш ніж 2–3 кнопками.

### 3.2. Детальна сторінка запису (Detail)

Використовується для перегляду окремого запису (проєкт, клієнт, угода тощо).

- **Структура:**
  - Заголовок сторінки (назва сутності) + ключові метрики/статуси.
  - Верхня панель дій (редагувати, змінити статус, архівувати тощо).
  - Основний контент:
    - або **дві колонки** (контент + сайдбар із метаданими),
    - або **таби** (Overview / Activity / Settings).

- **UX‑правила:**
  - Primary‑дія (наприклад, «Edit») має бути одна й очевидна.
  - Складні або руйнівні дії (delete, archive) розміщувати в dropdown / контекстному меню.
  - Важливі поля (статус, власник, дедлайн) мають бути видимі без скролу.

- **Для макетів Figma:**
  - Показати мінімум два стани: звичайний і стан, де деякі поля відсутні (щоб врахувати пусті значення).
  - Зазначити, які елементи клікабельні (іконки, бейджі, теги).

### 3.3. Форми та майстри (Wizard)

Форми будуються з використанням Nuxt UI + FormKit та базових компонентів (`components/base`).

- **Структура:**
  - Заголовок форми + короткий опис (що станеться після сабміту).
  - Поля, згруповані по логічних секціях (контактні дані, білінг, налаштування доступу).
  - Primary‑кнопка сабміту + вторинні дії (Cancel, Back).

- **UX‑правила:**
  - Не розміщувати занадто багато полів на одному екрані — краще розбити на кроки (wizard).
  - Обов’язкові поля позначати консистентно (наприклад, `*` та/або пояснення).
  - Помилки показувати біля поля + короткий summary‑меседж (за потреби).

- **Стейт‑патерни:**
  - **Loading**: заблокований сабміт, лоадер на кнопці або скелетон вмісту форми.
  - **Success**: чіткий візуальний фідбек (alert/inline‑повідомлення, редірект або оновлення сторінки).
  - **Error**: помилка валідації (під полем) vs помилка мережі/серверу (alert у верхній частині форми).

- **Для макетів Figma:**
  - Обов’язково показати приклади з помилками (мінімум 1–2 поля з error‑станом).
  - Передбачити текст підказок/help‑text (де ми пояснюємо формат, приклад тощо).

## 4. Стани інтерфейсу

### 4.1. Loading

Loading‑стани мають бути:

- **консистентними** між сторінками;
- **ненав’язливими**, але помітними;
- зрозумілими в контексті (користувач розуміє, що саме чекає).

Приклади реалізації (на рівні дизайну):

- Skeleton‑блоки для таблиць/карток.
- Лоадер у кнопці при сабміті форми.
- Radial/inline‑progress для тривалих операцій.

**У макетах:**

- Показати хоча б по одному прикладу skeleton‑стану для таблиці та картки.
- Для критичних дій (видалення, оновлення великого масиву даних) можна передбачити окремий loading‑екран/оверлей.

### 4.2. Empty state

Empty‑стейти важливі для UX, коли:

- у списку ще немає даних;
- фільтр/пошук не дав результатів;
- користувач тільки що зареєструвався й бачить «порожню» систему.

Рекомендований шаблон:

- Іконка/ілюстрація (лаконічна, не надто «гучна»).
- Короткий заголовок (що тут має бути).
- 1–2 рядки пояснення (чому пусто).
- CTA‑кнопка (створити перший запис / скинути фільтри / імпортувати дані).

**Для макетів Figma:**

- Показати приклади empty state для:
  - таблиці/списку;
  - дашборду (перший вхід);
  - форми/фільтра (нема збігів).

### 4.3. Error state

Є два основні типи помилок:

- **Локальні помилки валідації** (на рівні поля форми).
- **Глобальні помилки** (мережа, сервер, доступ).

Рекомендований шаблон:

- Для форм:
  - червона підсвітка поля;
  - коротке текстове пояснення під полем;
  - за потреби — глобальний alert зверху з узагальненням.

- Для сторінок:
  - компактний блок‑alert у верхній частині;
  - зрозумілий текст (без технічних кодів помилок для кінцевих користувачів);
  - опції: «Спробувати ще раз», «Повернутись назад», «Зв’язатися з підтримкою».

**У макетах:**

- Показати хоча б один приклад глобального error‑alert’а на сторінці.
- Для валідації форм — показати еррор для різних типів полів (input, select, textarea).

## 5. Маркетингові сторінки та блоки

Маркетингові сторінки збираються з блоків у `components/blocks` та описані в `docs/components/blocks.md`.

**Загальні принципи:**

- Більше «повітря» і більші заголовки, ніж у порталі.
- Ясна ієрархія: Hero → Social proof → Features/Steps → CTA.
- Обмежена кількість кольорів: primary, сірі, кілька акцентів для ілюстрацій/іконок.

**Для кожного типового блока бажано в Figma:**

- Показати базовий варіант (як у коді).
- Описати можливі варіації (зображення ліворуч/праворуч, один/два CTA, зі/без підзаголовка).

## 6. Як використовувати ці патерни дизайнеру

1. **Вибрати тип сторінки**  
   Визначити, чи це маркетингова, чи «портальна» сторінка з даними.

2. **Підібрати відповідний шаблон**  
   - Список → використовувати шаблон Dashboard/Listing.  
   - Деталі → шаблон Detail.  
   - Створення/редагування → шаблон Form/Wizard.

3. **Додати стани**  
   Для кожної ключової сторінки бажано мати в макетах:
   - заповнений стан;
   - empty state;
   - loading (за потреби);
   - error state (мінімум один приклад).

4. **Валідувати з токенами та компонентами**  
   Перед передачею макетів у розробку — звірити:
   - чи всі кольори/радіуси/шрифти відповідають `docs/design/index.md`;
   - чи використовуються (або можуть бути реалізовані) наявні компоненти з `components/*`.

Якщо новий сценарій не вкладається у наявні патерни, його варто описати окремо (відправна точка — найближчий існуючий шаблон з мінімальними змінами).
